Model Editor V22 - what Version 22 does
======================================================

This specification is rewritten whole at Finish Plan
V3 step #15 (Bit 16, piece 2b), from the root spec it
replaces. The root spec was written 2026-11-17 for
the Assembly: it carried the Version 21 specification
verbatim and recorded Bit 2 only, so it could not
state what Version 22 does. This rewrite states it.
Every claim below traces to a sealed step record -
the Finish Plan V3 COMPLETE markings for steps #1
to #13, the Bit 14 seal (step #13), and the Bit 15
close record (step #14) - and the limits those
records carry are stated here in plain words, not
dropped. Where a proof ran with no plugin connected,
this spec says so; nothing aspirational is stated
as built.

THE FILE
--------
Model_Editor_V22.HTML is one self-contained HTML
file: 9,199,023 bytes, MD5
0b07e0a42d8205e7ea60e1bfb6ad35de. It is Version 21's
editor carried whole - every Version 21 feature
stands in it - plus the fourteen steps of the
Version 22 Finish Plan, grafted cumulatively bit by
bit, each proven before the next started. The build
census over the final built file counts 391 of 391
markers present, missing []: the 174 Version 21
markers (names advanced) and 217 markers the steps
added. The editor is open source under the MIT
License (LICENSE, carried unchanged from Version
21's shipped copy). The standing product contract
carries from Version 21 unaltered: custom tools
built in; the Ai pipeline fully automated first,
each step adjustable afterwards and re-running from
that step; text fully visible, no scrollbars or
slide bars hiding it, panels resizable; and all
features requested carried in every version.

WHAT CARRIES FROM VERSION 21 (the base editor)
----------------------------------------------
- Per-point fill radius: selecting a joint point
  shows a Fill radius row (slider, typed number
  box, readout) whose range is centred on that
  point's own radius, 20% to 180% of it, so a
  wrist's slider tops out far below a hip's. The
  fill circle is centred on the point's pin and
  moves with it. Parts sharing one joint share
  the joint's radius. A point with no radius set
  shows the completion's computed default, marked
  "(auto)".
- Anatomical seeding: each joint's starting radius
  is measured from the joint's own local part
  width in the artwork - seed = round(1.42 x
  width/2) + 4, minimum 12, nothing hard-coded per
  joint name. Wrists and ankles measure smallest,
  hips, shoulders, neck, waist and spine largest.
- Persistence: radii live in the rig JSON
  (disc_radius per joint), in the GLBs (node
  extras and the top-level joints table), and in
  the editor's save roads (GLB open and save, the
  rig points file, undo snapshots).
- The reveal bitmap wins over the disc: per joint,
  the fill source is (1) the reveal bitmap - the
  model's own rendered pixels from 5-degree pose
  sweeps, composited - where one exists, and the
  engine then draws no disc for that joint at
  all; (2) the disc at the per-point radius, the
  manual path. The written rig and census record
  each joint's fill_source.
- The four-view input set: the Ai flow presents
  four pictures - front, back, left side, right
  side, any order - and the pipeline's detection
  names all four from the unordered set. A legacy
  three-picture set still classifies.
- Direction: 3D first, then paper. The automated
  chain runs Make the 3D model -> Snapshots ->
  Slice -> Redraw -> Rig it -> Make it paper, and
  the paper is derived from the 3D.

THE VERSION 22 STEPS
--------------------
1. TORRENT SECTIONS (Finish Plan #1). Heavy
   operations route through Torrent_Sections_V1.PY
   section by section, then a stitch pass runs
   over the whole model. The Sections panel shows
   the verdict: seam mismatches counted, the
   watertight verdict, the triangle count against
   the slider target, and the whole-model compare
   (a sectioned run equals a whole run, maximum
   difference 0.0 on a real model; a planted seam
   offset is caught and named). An operation is
   not reported done until the stitch pass says
   so. Scope, declared in the panel too: the
   torrent step carries geometry and COLOR_0
   only - not skinning, animation or textures -
   and a model with a skins array or JOINTS_0 /
   WEIGHTS_0 attributes is refused with a plain
   log line and the reason on the stitch line,
   never silently stripped. The detail step and,
   on large models, sculpt route through this
   same route.
2. BRUSHES (#2). The Brushes panel: paint writes
   COLOR_0 inside the brush's hardness falloff
   only; sculpt pushes or pulls along normals
   with adaptive split and collapse; erase
   restores only brush-selected edited vertices
   from the pristine copy of the loaded GLB the
   editor keeps on load. A sculpt is judged
   against the model's own starting state: it is
   refused when it ADDS jagged edges over the
   model's baseline, not for roughness the model
   already carries.
3. FULL LAYERS IN THE PAPER STEPS (#3). After
   slicing, the part layers run through
   Full_Layers_V1.PY so every part runs past its
   joint into the next part and each layer carries
   the full area the part above can uncover; the
   paper GLB is built from the completed set,
   inputs untouched. The completion report (per
   joint: worst uncovered count before, zero
   after) is written into the run log. Proven at
   zero revealed background on the man's parts and
   on Duke's parts through the editor's own
   pipeline. The per-point fill radius stays as
   the manual fallback where no completion data
   exists.
4. AUTOMATIC RIG POINTS (#4). The rig step places
   every automatic point at the centre of the
   overlap zone of the two parts it joins. The
   accuracy standard: trunk joints (neck,
   shoulders, waist, hips) within 5 percent of
   body height of the reference position; core
   joint heights within 2 percent of body height.
   Two named measured exceptions stand, asserted
   by name in the suite with their measured
   values, never silently: hips under
   overlap-centre (the pelvis part is a large
   blob, not the reference's pelvis disc, so its
   thigh-overlap centroid sits mid-thigh; the hip
   pins are governed by the trunk and height
   tolerances, which they pass) and shoulder_f
   under trunk and height (its far root is drawn
   low; its pin is governed by the overlap-centre
   tolerance, which it passes).
5. THE WIRED RIG CODE (#5). The paper data comes
   from the 2D views themselves: the 2D route
   stands on its own, a 3D build is never a
   required step, and the 3D sweep remains an
   optional extra source where a model already
   exists. Both #3's sweep test and #4's accuracy
   test were re-run against the wired code's
   output and pass.
6. THE OPEN PLUGIN POINT (#6) - see THE PLUGIN
   POINT'S TERMS below.
7. MORE MODELS ALONGSIDE (#7). Loading a GLB
   never replaces what is open: an added model is
   placed in the 3D view the way rig points are
   placed, moved to where it belongs, and its own
   X and Y directions can be changed for that
   object alone. The combined save holds both
   models, and the first model is provably
   untouched by the second's placement (its
   source byte-identical by MD5 in the gate).
8. EMOJI AND DESCRIPTION TO 3D (#8). An emoji is
   drawn with the device's own emoji font, cut
   out (BiRefNet through rembg, with the pinned
   clean fallback; the BRIA session is never
   pinned), and made 3D by the pipeline's
   existing make-3D step. A description takes the
   same road through the editor's own
   picture-making, or through the plugin point's
   expand when a plugin is connected. When the
   making needs a view the image set does not
   hold, the pipeline generates it and carries
   on, and the run log names what was generated.
   Every product of the chain lands in the Models
   list and can be detailed, sectioned, brushed,
   placed, and made paper. The Puppy Blender bake
   proof stands in this step's record: texture
   1024x1024, 574,765 of 591,049 island texels
   observed (97.2 percent) across all four
   cameras, sanity render IoU 1.0 - run on Puppy,
   not on a stand-in.
9. THE ANGLE DEGREES FIELD (#9). Beside the main
   angle slider, and on each part row, a number
   box: type a number, press Enter, the slider
   goes to it and the model's angle matches it.
   A change without Enter changes nothing; Enter
   clamps to 180.
10. THE AI TAB (#10). The tab holds the full
    step table of the AI pipeline - eight rows
    naming a best-fit model for every step:
    detail, generation, placement, rigging,
    coloring, polish among them. Each model is
    wired only where the wiring stays fluid and
    holds quality and accuracy; where it does
    not, that step runs on Glimmer alone, Glimmer
    being the standing fallback and judge. The
    three run modes live in the tab: full auto,
    where the models go through every step
    themselves; step by step, where the AI stops
    after each step for Solomon's word; and fully
    manual, where Solomon does it himself. Every
    step's output can be edited by hand in the
    tab before the next step consumes it - a
    manual gate at every step, and a hand edit in
    a step's gate field is the exact input the
    next step receives. With no model connected,
    the tab says so plainly and claims nothing.
11. DETAIL INTELLIGENCE (#11). The triangle
    slider's total is a whole-model budget, split
    across the model's parts by the detail map
    written in the Detail row's gate field: a
    named part gains detail, the rest stand, and
    the parts sum to the budget exactly, read back
    per part from the written GLB, watertight and
    stitch-clean. THE PARITY RULE, stated plainly:
    exactness holds only where the budget shares
    the model's total parity - every watertight
    move changes a closed part by an even count -
    so a budget whose parity differs from the
    model's total can never land exactly while
    watertight; the engine reports it
    parity_blocked with the neighbouring
    achievable totals and writes nothing. JUDGE:
    no plugin was connected in this step's proof,
    so no judge ran and no verdict is claimed -
    the hand-written gate-field map was the
    direction.
12. PART-BY-PART GENERATION (#12). The language
    model generates every part one by one - parts
    list first, then one job per part - then
    helps place each part on #7's machinery and
    rig it to #4's accuracy rule; the combined
    model stands in the editor. CLAIM LIMITS, from
    this step's seal: placement in the gate is
    exactly where the gate field tells it - a
    language model choosing placements is not
    proven by this step; and the six gate parts
    share one stand-in geometry, so no claim
    about distinct part shapes stands. JUDGE: no
    plugin was connected, so no judge ran and no
    verdict is claimed.
13. THE POLISH LOOP (#13). Coloring first: a
    colour specification in the Coloring row's
    gate field (part name and colour) is written
    as COLOR_0 on every vertex of each named part
    by the bridge "color" step and
    Color_Engine_V1.PY, read back from the written
    file; a part the model does not hold is
    refused by name and nothing is written. Then
    the polish loop: rounds of #11 refinement at
    written per-round budgets, each round gated
    in the tab, the triangle count rising per the
    budget, the result watertight and
    stitch-clean, colours standing in COLOR_0
    through every round. In step by step mode the
    loop stops after each round; a hand edit of
    the next round in the gate field is the
    direction it resumes on, and the edited
    budget is the budget it lands on. LIMITS,
    from this step's seal, stated plainly: no
    plugin was connected in any run, so no judge
    ran, no verdict is claimed, and NO JUDGED
    FINISH is claimed - the loop stopped because
    the written rounds are done. The references
    are names only, written by hand into the
    round specification and carried verbatim into
    the run log (one reference line per round);
    nothing was fetched or viewed online, and
    ACTUAL ONLINE-REFERENCE USE REMAINS UNPROVEN
    until a connected run on Puppy. A real judged
    finish likewise remains unproven until a
    connected run.
14. CROSS-DEVICE TORRENT CHUNKING (#14). An AI
    task from the tab is split into chunks as
    small as needed for quality results: the page
    parses a hand-written chunk specification and
    refuses prose; the bridge "chunk_task" step
    cuts one payload per chunk part and ledgers
    each chunk under the Cluster Switch assignment
    rule - capability first (a chunk naming a
    device the run does not hold, or a device
    without the driven step, is refused by name,
    never silently rerouted), then fastest
    measured route, then load. One executor
    program, the same on every device, receives a
    chunk under its manifest (per-chunk SHA-256
    verified on arrival), executes it on its own
    copy's bridge steps, and returns the output
    under a fresh manifest; the bridge
    "chunk_stitch" step collects the returns,
    refuses a chunk set that does not cover every
    input part by name, and stitches them in chunk
    order. The stitched output equals the
    single-device output three ways: per-part
    read-backs exact (maximum position difference
    0.0, faces and colours identical), geometry
    SHA-256 equal, and the single-device file
    rewritten through the same writer path
    byte-identical to the stitched file. A device
    dropping out mid-task loses no chunk: the
    missing chunks are named as the resume list,
    held verified chunks are never re-sent or
    re-executed, and the resume runs only the
    missing chunk. A chunk corrupted in transit is
    refused by name (CHUNK_HASH_MISMATCH) and
    repaired by a lone re-send. SCOPE LIMIT,
    stated plainly, from this step's close record:
    ALL OF THIS IS PROVEN ON STAND-IN DEVICE
    FOLDERS ON ONE MACHINE, driving the real
    transfer modules and the real bridge steps -
    it proves the machinery, not that any real
    device ran anything. NO REAL DEVICE HAS RUN A
    CHUNK: the Pup, Puppy and Wolf live legs are
    unproven, the step's own gate of two real
    devices stands unmet, and STEP #14 STANDS
    OPEN on those live legs. The offline surface
    is proven in shape only - a real disconnect
    mid-transfer, resumed from the offline queue,
    is unproven. No judge verdict exists for
    chunked work.

THE PLUGIN POINT'S TERMS (step #6, as sealed)
---------------------------------------------
The editor carries ONE marked plugin point, left
open for a third-party plugin that connects a
local language model to the Ai input. The plugin's
private GitHub repository is referenced by name
only; nothing of it is exposed or included. The
point loads a client file when one is configured
in Settings; the client's shape is
Describe_It_Client_V1.JS - health, expand, plan,
judge. Routing with a plugin connected: an emoji
or description goes to expand, then the editor's
own picture and model steps run; an instruction
like "add wings" goes to plan, and the editor
runs the returned steps with its own tools; a
finished torrent operation's stitch report and
rendered views go to judge, completing the final
pass. The editor itself contains no language model
and claims none: expanding, planning and judging
are the plugin's abilities when one is connected,
never built-in ones. With no plugin connected, the
Ai input behaves exactly as Version 21 left it,
and nothing in the page claims otherwise; until a
plugin is connected, the deterministic stitch
numbers alone gate a torrent operation. The AI
tab's per-step models wire at this same point,
under the same terms.
